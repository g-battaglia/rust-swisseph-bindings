# Native C source profiles

Native source profiling is an explicit build policy. An absent
`SWISSEPH_NATIVE_PROFILE_MODE`, or the value `off`, preserves ordinary native
compilation and linking. `use` applies the bundled counter profile; `generate`
creates diagnostic instrumentation. Neither policy changes public Rust/C APIs,
original native C/header expressions, data selection or calculation call order.
There is no runtime result cache, automatic training or speed guarantee.

## Supported modes and commands

Default `off` works with the ordinary supported build targets and links no Clang
profile runtime. A present non-Unicode mode or an unknown mode fails clearly.
The two opt-in modes require native Darwin arm64, Apple Clang 17, release O3/PIC/LTO,
an absolute compiler executable in `CC`, and an explicit installed `SDKROOT`.
Other targets/toolchains fail admission; there is no silent unprofiled fallback.
They reject implicit `CFLAGS`, `CPPFLAGS` and inherited `LLVM_PROFILE_FILE`.

The following paths describe an installed Command Line Tools layout. Set them
to the actual supported compiler and SDK; the build checks their identities.

```sh
export CC=/Library/Developer/CommandLineTools/usr/bin/clang
export SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk

env -u CFLAGS -u CPPFLAGS -u LLVM_PROFILE_FILE \
    SWISSEPH_NATIVE_PROFILE_MODE=off cargo build --release --locked --offline

env -u CFLAGS -u CPPFLAGS -u LLVM_PROFILE_FILE \
    SWISSEPH_NATIVE_PROFILE_MODE=use cargo build --release --locked --offline
```

`use` adds `-fprofile-instr-use=<packaged counts.profdata>` and rejects missing or
outdated records with `-Werror=profile-instr-missing` and
`-Werror=profile-instr-out-of-date`. It links no profile runtime and never trains,
merges, searches for a local profile or downloads one. The bundled profile is
not enabled by default.

For a separately reviewed diagnostic generation build, use an existing external
directory and the actual static runtime returned by that compiler:

```sh
export SWISSEPH_NATIVE_PROFILE_RUNTIME="$($CC -print-file-name=libclang_rt.profile_osx.a)"
mkdir -p /absolute/external/profile-raw
env -u CFLAGS -u CPPFLAGS -u LLVM_PROFILE_FILE \
    SWISSEPH_NATIVE_PROFILE_MODE=generate \
    SWISSEPH_NATIVE_PROFILE_RAW='/absolute/external/profile-raw/%p-%m.profraw' \
    cargo build --release --locked --offline
```

The raw path must be absolute, outside the source tree, end in `.profraw` and
include `%p` and `%m`. The runtime must be an absolute file named
`libclang_rt.profile_osx.a`, corroborated by the selected compiler. Its envelope
may be a thin ar archive or a bounded big-endian FAT32 archive containing one
exact arm64-all slice with valid bounds/alignment and archive magic. Other
universal formats require review. This envelope check is not a member/link audit.

Generation adds only `-fprofile-instr-generate=<pattern>` to the existing native
compiles and declares the static Clang runtime to the final Rust link. Building
alone executes no training workload. Actual final-image record retention,
archive/runtime selection, constructors and writer behavior need independent
inspection: an archive build or a C-only link does not prove the Rust final link.
Diagnostic root-retention linker options are not shipped profile-use options.
Any new generation requires a declared workload and record-policy review before
numerical execution; normal Cargo/package builds do not regenerate the bundle.

## Bundle and exact C context

The fixed resources under `native-profiles/source-v1` are:

- `descriptor.txt`: strict, duplicate-free `key=value` context fields;
- `counts.profdata`: the indexed source-counter profile;
- `audit.txt`: record-kind, final-link, training and external-path evidence;
- `training-inputs.json` and `training-configuration.json`: the declared input
  and configuration manifests, not calculated outputs.

The recorded training set contains 55 declared workloads, one process per case,
three warm calls and thirty further real calls each: 1815 workload calls. Normal
preparation also enters the profile. All declared cases are retained; there is
no retry, selective merge or favorable timing selection. The original counter
profile and training input/configuration bytes remain unchanged by package
metadata handling; only the exact context/provenance metadata is rebound.

The admitted profile records contain execution counters and structural names/
hashes, not astronomical arguments, coordinates, calculated outputs or residuals.
The inspected object records have zero sites for all three value kinds, zero
bitmap sites and no instrument-value calls. An altered instrumentation graph
requires a new actual record audit; these findings do not authorize arbitrary
profile formats or memory/value recording.

The descriptor binds the actual C/header/generated bytes, owned emitters/helpers,
`build.rs`, source pins, compiler/version, target, ordinary flags and SDK settings,
plus all bundle checksums and training-tool/runtime provenance. Unknown/missing
fields, changed resources or a different admitted graph fail before native object
compilation. Stable content labels omit checkout/OUT_DIR prefixes; profile
function names themselves are never rewritten, normalized or guessed. Actual
complete static-name/hash matching was checked from distinct external source and
Cargo output paths with strict diagnostics enabled.

Cargo may normalize the effective `Cargo.toml` when packaging. Its incidental
bytes are excluded only from the C-graph context fingerprint. The active manifest
is recorded separately as `effective-cargo-manifest-fnv1a64: <checksum>` in
`native-profile-inputs.txt`; the colon keeps it outside descriptor context fields.
The build never selects or trusts a `Cargo.toml.orig` alias. Source and extracted
package builds can therefore have equal C context and different effective-manifest
provenance. Complete authored/effective manifests and package/source trees remain
independently bound with SHA-256 during qualification.

The build uses explicitly labelled FNV-1a checksums for content provenance; these
are not cryptographic authentication. Independent evidence freezes the complete
bundle and source/package inputs with SHA-256. Every policy variable and used
resource is a Cargo rerun input. Cargo includes the resource directory;
`native-inputs.txt` names the private policy and `native-profile-inputs.txt`.
Original licenses and notices remain part of the package.

## Verified scope and limits

The current profile-use source passed 337 Rust/doctest checks, 1347 unrestricted
smoke cases, formatting, strict Clippy and private Rustdoc. Both ordinary source
and Cargo-normalized extracted-package use builds passed with identical C context
and all eleven generated native C/header inputs; their effective manifest
provenance differs as expected. Negative controls for an altered profile, unknown
descriptor field, changed owned native header and changed public native header
were rejected before any C object was emitted. Depending on the input, rejection
comes from the context guard or an earlier pinned-source guard.

Independent profile-use native controls passed exact comparisons in all four
rounding modes, including native output/state, errno and sticky-flag checks, with
separate scalar-fallback controls. This does not establish a global floating-
environment contract or independent scientific accuracy.

The corrected extracted-package actual archive also passed independent exact
four-mode controls: 36,000 whole-engine comparisons, 4,160 state transitions,
4,160 subsequent ordinary calls, 5,760 matrix cases and 80 fallback controls.
The positive native-source fallback subset contains 800 comparisons. The entire
actual Cargo archive was linked, with all ten native object payloads positively
identified. Output arrays, diagnostics, state, errno and the floating environment
were compared in memory; only input identities and pass/fail counts were saved.

With the mode variable absent, all six metadata tests pass, the provenance is
exactly ordinary mode, all eleven generated C/header inputs match profile-use,
and no profile runtime or counter symbol is present. Identical C source alone
does not establish identical floating-point lowering. Every delivered artifact
must retain its own source/compile/link identity and required numerical controls.

No performance result or speed target follows from these build and correctness
checks. Portable CPU options, floating-point precision, native flags, inputs and
call order remain unchanged; no fast-math, approximation, reduced precision,
profile-name suppression or calculated-result cache is permitted.
